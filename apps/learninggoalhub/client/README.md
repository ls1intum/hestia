# LearningGoalHub Client

Vite + React 18 + TypeScript + Tailwind CSS client for the LearningGoalHub server. Which component
renders which part of the UI, the query keys and the styling tokens are in
[docs/CLIENT.md](../docs/CLIENT.md).

## Development

```bash
npm install
npm run dev        # http://localhost:5173/learninggoalhub/
```

The app lives under the `/learninggoalhub` path prefix, in development as in production. The dev
server proxies `/learninggoalhub/api` to the Spring server (`http://localhost:8080` by default,
override with `VITE_API_TARGET`) and strips the prefix, as the production proxy does. Start the
database and server first; the [app README](../README.md#run-locally) has the commands, including
the throwaway SAML key pair the server needs to boot.

## API client

Types are generated from the server's OpenAPI schema with
[`openapi-typescript`](https://openapi-ts.dev) and consumed through a typed
[`openapi-fetch`](https://openapi-ts.dev/openapi-fetch/) client (`src/api/client.ts`).

`openapi/openapi.json` is a checked-in snapshot of the server's `/v3/api-docs`, and
`OpenApiSnapshotTest` in the server tests fails when the two differ. After a server API change,
regenerate both files from the repository root (Docker must be running; no server or `.env` is
needed):

```bash
UPDATE_OPENAPI_SNAPSHOT=1 ./gradlew :apps:learninggoalhub:server:test --tests '*OpenApiSnapshotTest' --rerun-tasks
cd apps/learninggoalhub/client && npm run generate:api && npm run typecheck
```

The server sorts the document's keys, so the diff shows only what changed. Responses other than
the one springdoc infers from the return type (a `202`, a `204`, a `409` the client handles) need
an `@ApiResponse` on the controller method, as `ExtractionController.extract` has; otherwise they
are missing from the types.

## Scripts

- `npm run dev` – start the dev server
- `npm run build` – typecheck (`tsc -b`) and production build
- `npm run typecheck` – typecheck only
- `npm run lint` – ESLint
- `npm test` – Vitest. Helper tests run in Node; component tests (`*.test.tsx`) opt into jsdom with a `// @vitest-environment jsdom` header and import `src/test/dom.ts`, and mock `src/api/client.ts` instead of calling a server.
- `npm run e2e` – the browser tests (see below)
- `npm run generate:api` – regenerate `src/api/schema.d.ts` from `openapi/openapi.json`

## Browser tests

`e2e/*.e2e.ts` drive the real client and server through Chromium with
[Playwright](https://playwright.dev): creating a course, extraction, the skill review, editing,
the source pane, CSV export, deletion, and what the user sees when an upload, a save or a model
call fails. No real model is called. `e2e/fake-llm.mjs` stands in for the gateway, recognises each
prompt by the JSON it asks for, and answers from the prompt's own lines. The test PDFs are
generated by `e2e/pdf.ts`.

Playwright starts the fake model (port 4010), the server jar (8090) and a Vite dev server (5174)
itself. It needs a Postgres on port 5433 and a built jar:

```bash
docker run -d --rm --name learninggoalhub-e2e-postgres -p 5433:5432 \
  -e POSTGRES_DB=learninggoalhub -e POSTGRES_USER=learninggoalhub -e POSTGRES_PASSWORD=learninggoalhub \
  pgvector/pgvector:pg16
./gradlew :apps:learninggoalhub:server:bootJar              # from the repository root
npx playwright install chromium                             # once
npm run e2e
```

Each test creates its own course, so the database can be reused between runs. CI runs the same
suite (`test-e2e` in `.github/workflows/learninggoalhub-cicd.yml`) and keeps the Playwright report of a
failed run as an artifact. When a pipeline change sends a prompt the fake does not know, the server
log shows the fake's `400` and the fake prints the start of the prompt; teach `answer()` the new
shape.
